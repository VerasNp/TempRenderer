# ADR-000: Escolha inicial de toolchain

## Contexto

Para início do projeto será necessário uma escolha de um conjunto de
ferramentas de desenvolvimento, dentre elas: meta-system build, backend
system build, compilador, formatador, linter, test-runner e framework
(testes).

## A ser considerado

- Meta-System Build:
  - CMake        (padrão de facto, maior ecossistema/integração com IDEs)
  - Meson        (mais moderno, sintaxe mais limpa, build mais rápido)
  - Bazel        (se o foco for monorepo/escala, builds hermeticamente reprodutíveis)
- Backend system build:
  - Ninja        (rápido, baixo overhead, padrão junto com CMake/Meson)
  - Make         (mais tradicional, maior familiaridade, presente em quase todo ambiente)
- Compilador:
  - Clang        (mensagens de erro melhores, ferramentas de análise integradas — clang-tidy/format)
  - GCC          (maior maturidade em Linux, suporte extenso a extensões/plataformas)
- Formatador:
  - clang-format (padrão de mercado, integra com Clang/clang-tidy, configurável via .clang-format)
  - Uncrustify   (mais flexível para estilos legados/específicos, porém mais complexo de configurar)
- Linter:
  - clang-tidy   (mais completo, verificações modernas de C++, integra com clang-format)
  - cppcheck     (independente do Clang, foco em detecção de bugs reais, baixo falso-positivo)
- Test-runner:
  - CTest        (nativo do CMake, orquestra múltiplos executáveis de teste)
  - Runner embutido do framework escolhido (GoogleTest/Catch2/doctest rodam standalone também)
- Framework (testes):
  - GoogleTest   (mais adotado no mercado, mocks integrados via gmock, grande comunidade)
  - Catch2       (header-only, sintaxe moderna, fácil de embutir)
  - doctest      (mais leve/rápido de compilar que os anteriores, boa opção se build time for crítico)

## Decisão

Será usada a seguinte configuração:

- Meta-System Build: CMake
- Backend system build: Ninja
- Compilador: Clang
- Formatador: clang-format
- Linter: clang-tidy
- Test-runner: CTest
- Framework (testes): doctest

## Consequências

- **Escopo Linux-only inicialmente**: não há necessidade de considerar MSVC
  ou toolchains específicas de Windows/macOS neste momento. Suporte a outras
  plataformas fica fora do escopo desta decisão e pode exigir revisão futura
  (ex: adicionar MSVC ao CI se houver demanda por suporte a Windows).

- **GCC não é o compilador principal, mas deve ser validado em CI** como
  segundo compilador, já que é o mais usado em distribuições Linux e ajuda a
  garantir portabilidade do código dentro do próprio ambiente-alvo.

- **Explicit template instantiation**: como a lib usa templates para
  suportar `float`/`double` mas mantém separação `.h`/`.cpp`, será
  necessário instanciar explicitamente os tipos suportados em cada `.cpp`
  (`template class Vec3<float>`, `template class Vec3<double>`). Adicionar
  suporte a um novo tipo no futuro exige alterar a implementação, não só o
  header.

- **LTO recomendado no build de release**: como a separação `.h`/`.cpp`
  limita o inlining do compilador em operações críticas de performance
  (`operator+`, `dot`, etc.), será necessário habilitar Link-Time
  Optimization (`INTERPROCEDURAL_OPTIMIZATION` no CMake) nos builds de
  release para mitigar o overhead de chamada de função nesses casos.

- **doctest exige rebuild da lib de testes a cada alteração**, mas por ser
  header-only e ter tempo de compilação menor que GoogleTest/Catch2, o
  impacto no ciclo de desenvolvimento é reduzido — trade-off aceitável dado
  o foco em iteração rápida.

- **CMake como meta-build** garante que a lib seja facilmente consumível por
  outros projetos via `find_package()` ou `FetchContent`, ao custo da maior
  verbosidade/complexidade da linguagem de configuração do CMake em
  comparação a alternativas como Meson.
